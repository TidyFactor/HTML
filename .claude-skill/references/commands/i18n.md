# Command: `i18n` — Translation & RTL/LTR Localization

## Purpose
Centralize translatable strings into dictionaries and make the site
correctly bilingual/RTL — without a server to pick the language per
request.

## When to run it
- `compo`/`pages` are stable (always last — see SKILL.md sequencing).
- User says "make this bilingual", "add Arabic", "add RTL support", or
  runs `i18n`.

## What it does
1. Extract every user-facing string into `/data/i18n/en.json` and
   `/data/i18n/ar.json` (or however many locales), keyed consistently
   (`nav.home`, `hero.title`, ...) — never by raw English text as the key.
2. Mark translatable spots in markup with `data-i18n="nav.home"` — this
   works identically whether resolved at build time or runtime.
3. **Prefer build-time dual-tree rendering for SEO**: `build.js` renders
   two full static trees, `/dist/en/` and `/dist/ar/`, each with the
   correct `<html lang dir>`, real translated text baked into the HTML
   (crawlable, no flash-of-untranslated-content), and `<link rel=
   "alternate" hreflang>` cross-linking the two. This is the default —
   only fall back to pure runtime swap (JS reads `data-i18n`, swaps text
   after load) if the project has no build step at all (runtime Web
   Components mode), and flag the SEO/FOUC tradeoff when you do.
4. Add a visible language switcher linking `/en/...` ↔ `/ar/...`
   (build-time) or toggling the dictionary + `dir` attribute at runtime.
5. RTL: verify layout with logical CSS properties (`margin-inline-start`
   over `margin-left`, etc.) rather than a separate RTL stylesheet where
   possible; flag any hardcoded LTR-only spacing/icons.

## Output convention
```
Build-time (recommended):
/data/i18n/en.json
/data/i18n/ar.json
/dist/en/... (full static tree, lang="en" dir="ltr")
/dist/ar/... (full static tree, lang="ar" dir="rtl")

Runtime fallback:
/data/i18n/en.json, ar.json  + data-i18n attributes + JS swap on load
```

## Checklist
- [ ] No hardcoded user-facing string left outside a dictionary
- [ ] Every locale's `<html lang dir>` is correct
- [ ] `hreflang` alternates present (build-time mode)
- [ ] RTL verified visually, not just `dir="rtl"` slapped on
- [ ] Language switcher present and working both directions
